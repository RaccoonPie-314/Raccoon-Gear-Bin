## Layout

```
app/
├── pages/            layout + composition only — no queries, no row mapping, no mutations
│   ├── index.vue     catalog home: grid, sidebar, control row, admin editor modals
│   ├── products/[id].vue   detail page (uses useCatalog)
│   ├── products/index.vue  redirect shim to /  (note: NOT app/pages/index.vue)
│   └── admin/login.vue
├── composables/
│   ├── useCatalog.ts         the only public catalog data layer
│   ├── useCatalogBrowse.ts   browsing state: search / sort / category / filteredProducts
│   └── useAdminAuth.ts       admin identity
├── components/       presentational; never import a data composable
│   ├── category/     CategoryNav (facade) + CategoryDesktop + CategoryMobile
│   └── …
├── middleware/       admin-auth.global.ts — guards /admin/*
├── types/            database.ts (schema mirror), catalog.ts (view models)
└── assets/css/main.css   theme + the select-morph keyframes
server/utils/supabase.ts  unused (see Known gaps)
```

## Boundary rules

1. **Public catalog data is fetched and mapped in exactly one place: `useCatalog`.** A page
   must not call `.from('products')` / `.from('categories')`, map a row, or build a storage
   URL. This rule exists because a second private copy of that path lived in `index.vue`
   for a long time, quietly drifted (English-only category names, `slug`/`status` missing
   from its select), and read as intentional because the generated wiki described the
   unified version.
2. **`useCatalogBrowse` owns browsing state and nothing else** — no network, no DOM, no
   refs to components. Search, sort and category selection are one interaction with three
   inputs (`filteredProducts`), not three features.
3. **Components under `app/components/` stay presentational.** They receive typed props and
   emit events; they do not import `useCatalog`. This already holds; keep it.
4. **Locale resolution has one implementation:** `pickTranslation` inside `useCatalog`
   (current locale → `en` → first available). Never resolve a translation inline.

## The Supabase typing contract — two rules that fail silently

`useSupabaseClient<Database>()` is deliberately **not** cast to `any`. The cast was removed
in Phase 1, and it was covering up two real defects, not laziness. Both failures produce
*no compile error* — every query just resolves to `never` — because `skipLibCheck` is on and
hides the constraint violation inside the library's `.d.ts`.

1. **Row shapes must be `type X = { … }`, never `interface X { … }`.**
   Supabase's `GenericSchema` requires `Row extends Record<string, unknown>`. TypeScript
   grants an implicit index signature to object *type literals* and **not** to interfaces.
   An interface row makes every query on that table silently unusable.

2. **`Views` / `Functions` / `Enums` / `CompositeTypes` must be `{ [_ in never]: never }`,
   never `Record<string, never>`.**
   A string index makes `keyof Views` resolve to `string`, so the *view* overload of `from()`
   matches every table name and types the relation as `never`. Symptom: `from('no_such_table')`
   compiles cleanly and every `data` is `null`.

Row types handed to the mappers are **derived from the queries themselves**:

```ts
type ProductRow = Exclude<Awaited<ReturnType<typeof productsQuery>>['data'], null>[number]
```

Select strings must therefore stay inline literals — building one with `.join()` or a
template degrades every row to `any`. With the derivation above, dropping a column from a
select breaks the mapper at compile time instead of handing the view an `undefined`.

`Relationships` in `database.ts` mirrors the real foreign keys from the migration. It is
what makes embedded selects (`product_translations(…)`) type-resolve; empty relationships
collapse an embed to `never`.

## Data flow (home page)

```
index.vue → useCatalog().fetchCatalog()
              ├─ fetchProducts()    published, created_at desc, embeds translations+images+category
              └─ fetchCategories()  is_active, sort_order asc, embeds translations
           → { products, categories } assigned to page refs
           → useCatalogBrowse(products) → { search, selectedCategory, sortOrder, filteredProducts }
           → template renders filteredProducts
```

`'newest'` sort is not a client sort — it is the server's `created_at desc` order, untouched.

## Desktop vs mobile: what must stay separate

`CategoryNav.vue` is a thin facade that renders both variants behind breakpoint classes.
Keep the split where it reflects a genuinely different input model:

| Must stay separate | Why merging would be wrong |
|---|---|
| Desktop vs mobile drag engines | mouse Y-axis + `grabOffsetY` vs touch X-axis with axis-lock detection, `scrollLeft` compensation, `preventDefault` only when `cancelable` |
| Selection-indicator transform | desktop = pointer-distance cosine magnification; mobile = fixed `1.5 + dragStretch` |
| Mobile carousel centring | `scrollActiveMobileItemIntoView` has no desktop analogue |
| Mobile bottom-bar `Teleport` + hide/show | desktop is sticky in normal flow |
| SearchDock desktop vs mobile launcher | different anchors and reveal conditions |

| Should be shared (currently duplicated) | Where |
|---|---|
| Category item model + active matching | ~110 identical lines in both category components |
| The six category icons | copied into both templates |
| Indicator geometry scaffolding (observers, `fonts.ready`, watches) | both components |
| Scroll-direction hide/show rule (60 / 6) | `SearchDock` **and** `CategoryMobile` — two window listeners, one behaviour |

## Interaction invariants

These numbers are tuned, not arbitrary. Changing one is a design decision, not a refactor,
and none of them are visible to the compiler or to `build`.

| Constant | Value | Where |
|---|---|---|
| Spotlight open / close morph | 420ms / 380ms, `cubic-bezier(0.33, 1, 0.68, 1)` | `SearchDock.vue` |
| Backdrop in / out, content in / out / delay | 260/200ms, 220/140ms/150ms | `SearchDock.vue` |
| Search-field collapse hysteresis | gone at `0`, back at `24` | `SearchDock.vue` |
| Dock reveal threshold / direction delta | `60` / `6` | `SearchDock.vue`, `CategoryMobile.vue` |
| Desktop magnification | `maxDistance 120`, `maxScale 0.15`, drag scale `×1.1` | `CategoryDesktop.vue` |
| Indicator slide | 260ms `cubic-bezier(0.16, 1, 0.3, 1)` | `CategoryDesktop.vue` |
| Mobile drag scale / axis-lock thresholds | `1.5 + stretch`; `\|dx\|>6`, `\|dy\|>10` bail | `CategoryMobile.vue` |
| Select panel morph | in 300ms from `scaleY(0.24)`, out 200ms ease-in | `main.css` |

`0.24` is trigger-height ÷ panel-height, so the panel grows out of the control instead of
popping beside it. The exit uses an accelerating curve on purpose: a decelerating collapse
leaves an opaque remnant motionless under the pill, which reads as a hang.

## Control language

`app/app.config.ts` is the single owner of pill shape and elevation for buttons, inputs and
selects — restyle there, not per call site. All single-line controls in the storefront are
**44px** tall, and the search pill's left edge is the product grid's left edge at every
breakpoint. Note: `app.config.ts` currently emits 3 pre-existing `tsc` errors (its `base`
key belongs under `slots.base` in Nuxt UI 4) — known, unfixed, do not "fix" it as a
drive-by; verify the pill styling still measures correctly if you touch it.

## Cross-component contracts to preserve

- `[data-search-anchor]` — `SearchDock` measures this element to decide when to collapse.
  It is a string contract with no type checking: rename or move the element in the same
  commit as the change, never across two.
- `SearchDock`'s desktop launcher is absolutely positioned against the `<aside>`; it only
  centres correctly because that element is `relative`.
- `CategoryMobile` teleports itself to `body`, so DOM order ≠ visual order.

## Where new code goes

- New read of catalog data → extend `useCatalog` (and its derived row type).
- New filter/sort/selection state → `useCatalogBrowse`.
- New shared UI with no data access → `app/components/`.
- Admin mutation → **PROPOSED** `features/admin/`; today it still lives in `index.vue`
  (see Known gaps) — do not add more of it there.
- New env var → both `.env.example` and `runtimeConfig` in `nuxt.config.ts`.

## Known gaps (Phase 2+ targets, not current behaviour)

- **Admin logic is not separated.** The `admin_users` existence check is written four times
  (`middleware/admin-auth.global.ts`, `useAdminAuth.isAdmin`, `useAdminAuth.isSuperAdmin`,
  `admin/login.vue`), and `index.vue` owns the editor form, the multi-table save and the
  delete flow.
- **Three hand-rolled headers** (`index.vue`, `products/[id].vue`, `admin/login.vue`) compose
  the same logo + theme + language controls with different sizes.
- **Dead code:** `app/types/product.ts`, `app/types/database.types.ts`, the `ProductCategory`
  union (the schema stores categories as rows, not an enum), `TemplateMenu.vue`, `AppLogo.vue`.
- **No `server/api` tier.** `createSupabaseAdminClient()` has zero callers and the
  service-role key is wired into `runtimeConfig` unread. All data access is the browser's
  anon client governed by RLS — which is the actual security model here.
- **No tests, no typecheck script.** CI runs `bun run build` only, which does not type-check.
- **Generated pages that describe absent capabilities.** `Supabase Integration/Real-time
  Features & Subscriptions.md`, `Testing & Quality Assurance/Testing Framework & Setup.md`,
  `Performance Optimization/Caching Patterns.md` and `Deployment & DevOps/Monitoring &
  Logging.md` are written as
  how-to guidance, not as descriptions of this codebase. There is no realtime subscription,
  no test runner, no cache layer and no monitoring integration. Read them as **PROPOSED**.
- **No category CRUD** in the UI, although RLS permits it. Generated docs that describe
  category administration are **PROPOSED**, not current.

## Verifying a change

```bash
bun run build                                            # what CI runs
./node_modules/.bin/tsc -p .nuxt/tsconfig.app.json --noEmit   # .ts only; .vue needs vue-tsc
```

`tsc` cannot parse `.vue`, so template bindings are not covered — the IDE language server
is, and it has caught real regressions here. For anything visual or interactive, measure:
drive headless Chrome over CDP at 1440 / 1280 / 1024 / 834 / 640 / 390 and assert geometry
(alignment, control heights, no horizontal overflow) and animation state (running
`getAnimations()`, snap delta, settle size) rather than eyeballing screenshots.
