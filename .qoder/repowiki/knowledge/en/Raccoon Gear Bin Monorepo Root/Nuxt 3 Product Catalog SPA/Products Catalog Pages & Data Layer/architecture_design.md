Three cooperating layers under `app/`:
- Pages (`app/pages/`): `index.vue` is the catalog home — it calls `useCatalog().fetchCatalog()` for data, hands the loaded list to `useCatalogBrowse` for search/sort/category filtering, and renders the grid, the category sidebar, the search dock and the admin editor modals. `products/[id].vue` is the product detail route — it resolves the id from the Nuxt router, calls `useCatalog().fetchProduct`, renders an image gallery with thumbnail selection, parses the `specifications` field (JSON array → object → newline-delimited key:value fallback) via a `parsedSpecs` computed, and sets SEO title through `useHead`. `products/index.vue` (not `index.vue`) is the redirect shim to `/`.
- Composables (`app/composables/`): `useCatalog.ts` is the single data-access layer for public catalog data — `fetchCatalog`, `fetchProducts`, `fetchProduct`, `fetchCategories` plus the `parseSpecifications`/`formatSpecifications` pair. It centralizes locale-aware translation resolution (current locale → English → first entry) in one `pickTranslation` helper, public URL generation via Supabase Storage bucket `product-images`, and mapping raw rows into the typed `CatalogProduct` / `CatalogCategory` shapes from `~/types/catalog`. `useCatalogBrowse.ts` owns browsing state only — `search`, `selectedCategory`, `sortOrder` and the derived `filteredProducts` — and performs no data access.
- Component (`app/components/ProductCard.vue`): presentational card displaying a product's first image, name, short description, price, stock status, and a link to `/products/${id}`; emits an `edit` event when the optional `isAdmin` prop is set.

Dependency direction: pages → `useCatalog` (data) and `useCatalogBrowse` (view state) → Supabase client. No page issues its own `products`/`categories` query or maps rows itself — there is exactly one implementation of each. Components are pure presentational consumers of `CatalogProduct` and do not import the composable directly.

Typing contract in `app/types/database.ts` — two rules that are not cosmetic, and breaking either one silently degrades every query to `never` rather than producing an error:
- Row shapes are declared as `type X = { ... }`, never `interface X { ... }`. Supabase's `GenericSchema` requires `Row extends Record<string, unknown>`, and TypeScript only grants an implicit index signature to object *type literals*.
- `Views`, `Functions`, `Enums` and `CompositeTypes` use `{ [_ in never]: never }`, never `Record<string, never>`. A string index makes `keyof Views` resolve to `string`, so the view overload of `from()` matches every table name and types the relation as `never`.

`skipLibCheck` is on, so both mistakes surface as unusable data rather than compile errors; `useSupabaseClient<Database>()` is deliberately not cast to `any`, which is what keeps the derived `ProductRow` / `CategoryRow` types honest.
