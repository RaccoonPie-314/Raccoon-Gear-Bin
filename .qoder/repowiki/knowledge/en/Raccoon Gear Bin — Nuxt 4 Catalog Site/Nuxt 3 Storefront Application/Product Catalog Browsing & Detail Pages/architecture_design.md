Three cooperating layers under `app/`. The authoritative rules live in `ARCHITECTURE.md` at the repo root — this card summarises them and loses to that file on any disagreement.

- Pages (`app/pages/`): `index.vue` is the catalog home — it calls `useCatalog().fetchCatalog()` for data, hands the loaded list to `useCatalogBrowse` for search/sort/category filtering, and renders the grid, the category sidebar, the search dock and the admin editor modals. `products/[id].vue` is the product detail route — it resolves the id from the Nuxt router, calls `useCatalog().fetchProduct`, renders an image gallery with thumbnail selection, parses the `specifications` field (JSON array → object → newline-delimited key:value fallback) via a `parsedSpecs` computed, and sets SEO title through `useHead`. `products/index.vue` (not `index.vue`) is the redirect shim to `/`.
- Composables (`app/composables/`): `useCatalog.ts` is the only public catalog data layer — `fetchCatalog`, `fetchProducts`, `fetchProduct`, `fetchCategories`, plus the `parseSpecifications`/`formatSpecifications` pair. Locale-aware translation resolution (current locale → English → first entry) lives in one shared `pickTranslation` helper used by product names, category names and the nav; public URLs come from Supabase Storage bucket `product-images`. `useCatalogBrowse.ts` owns browsing state only — `search`, `selectedCategory`, `sortOrder`, `filteredProducts` — with no network and no DOM access.
- Component (`app/components/ProductCard.vue`): presentational card displaying a product's first image, name, short description, price, stock status, and a link to `/products/${id}`; emits an `edit` event when the optional `isAdmin` prop is set.

Dependency direction: pages → `useCatalog` (data) and `useCatalogBrowse` (view state) → Supabase client. No page issues its own `products`/`categories` query or maps rows itself. Components are pure presentational consumers of `CatalogProduct` and do not import a data composable.

Typing contract in `app/types/database.ts` — two rules that are not cosmetic, because breaking either one silently degrades every query to `never` without producing a compile error (`skipLibCheck` hides the constraint violation):
- Row shapes are `type X = { … }`, never `interface X { … }`. Supabase's `GenericSchema` requires `Row extends Record<string, unknown>`, and TypeScript grants an implicit index signature only to object type literals.
- `Views`, `Functions`, `Enums` and `CompositeTypes` use `{ [_ in never]: never }`, never `Record<string, never>`. A string index makes `keyof Views` resolve to `string`, so the view overload of `from()` matches every table name and types the relation as `never`.

`useSupabaseClient<Database>()` is deliberately not cast to `any` — that cast previously masked both defects. Mapper row types are derived from the queries themselves, so removing a column from a select breaks the mapper at compile time; select strings must stay inline literals for that parsing to work.
